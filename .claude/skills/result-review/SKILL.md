# 結果檢討

> 這是**挖空模板**。標 ★ 的地方要你自己填。
> 重點是「看到什麼現象 → 代表什麼問題 → 下一次怎麼改」，讓 AI 像店長一樣檢討。

## 什麼時候用

每跑完一次 `npm run simulate`，要決定下一版策略怎麼改時。

## 試算結果裡有哪些線索

試算工具每天會印出：客人數、收入、備貨、宣傳、報廢（清潔費）、淨利、任務、星等、資金，以及「沒買到的客人」：

| 線索 | 意思 |
|---|---|
| 賣完買不到 | 有人想買，但貨不夠 |
| 嫌太貴 | 價格超過客人剩下的預算 |
| 想吃的沒上架 | 客人想吃的菜今天沒賣 |
| 因為討厭的菜不進門 | 上架了某位客人討厭的菜 |

## 對症下藥表

| 看到的現象 | 代表的問題 | 下一次怎麼改 |
|---|---|---|
| 賣完買不到很多 | 備貨太少 | 那樣菜多備一些（注意合計不能超過 80 份） |
| 報廢 15 份以上 | 推測：備貨比實際想買的人數多。規則書：報廢 6～15 份超過 5 份的部分每份 3 元，16 份以上再加 50 元大型廚餘清運費。需先看盤點確認是哪一樣菜報廢最多 | 把報廢最多的菜，備貨減到「賣出」份數（盤點建議值）；一次只動報廢最多的一兩樣，並說明預期省下的備貨成本與清潔費 |
| 嫌太貴很多 | 推測：價格超過客人剩下的預算。觀察要先確認是哪一天、哪樣菜被嫌 | 在可定價範圍內對那樣菜小幅降價，並說明可能犧牲單份收益；一次只改一樣，下一版再看「嫌太貴」有沒有減少 |
| 想吃的沒上架很多 | 推測：菜單沒有涵蓋客人想吃的東西（客人最多兩樣想吃的）。要先查是哪一樣菜被需要 | 把被需要的菜換進上架（最多 4 樣、合計 ≤ 80 份），並說明換掉了哪一樣、為什麼；注意換掉的菜可能原本也有客人要 |
| 因為討厭的菜不進門 | 推測：上架了某位客人討厭的菜，他直接不進門（也不留評價）。要先查是哪位客人、討厭哪一樣 | 評估該菜帶來的收入與損失的來客，若損失較大就取消上架那一樣，並說明取捨 |
| 星等往下掉 | 推測：不滿的客人比例太高（規則書：不滿 ≥ 25% 星等 −0.5，≥ 40% 星等 −1）。要先確認不滿是來自賣完、沒上架還是太貴 | 先修掉造成最多不滿的原因，因為星等會影響隔天的來客數（×0.6～×1.4），不要同時改太多地方 |
| 宣傳後增加來客，但淨利未改善 | 推測：新增客人帶來的收入，不夠抵過宣傳費與多備的貨。不能直接假設是宣傳沒用，要先看數字 | 先核對新增收入、備貨成本與宣傳費：新增收入 − 新增成本 − 宣傳費是否 > 0。若沒有，降低宣傳費（500 → 200 或 0）或調整備貨量，再提出一項修改 |

## 步驟

1. 讀試算結果，逐天找出上表的現象
2. 每一個現象，照對症下藥表提出一個修改
3. **一次最多改 3 個地方**，這樣才知道是哪個修改有效
4. 把修改後的策略存成新的檔案（例如 `plans/v2.json`），不要覆蓋舊的，方便比較

## 回報格式

```text
這一版的結果：最終資金 …、星等 …、報廢 …
發現的問題：
1. 第 N 天：（現象）→（問題）
修改：
1. …
下一版檔名：
```

## 不准做的事

- 不准修改遊戲檔案（`src/` 底下的任何檔案、客人包）
- 只能新增或修改 `web-lab/plans/` 裡的策略檔
